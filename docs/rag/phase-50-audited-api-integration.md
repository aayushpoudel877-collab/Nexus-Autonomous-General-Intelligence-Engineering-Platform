# Phase 50 — Authenticated Agentic Retrieval and Provenance Audit

## Implemented scope

- Adds an authenticated `POST /api/v1/rag/agentic-query` API boundary.
- Exposes one explicitly allowlisted, read-only lexical retrieval tool; no model-generated plan or write-capable tool is connected.
- Derives organization scope only from the authenticated user's membership; request bodies cannot select a tenant.
- Applies strict query, top-k, argument, timeout, output, step, and evidence bounds.
- Keeps retrieved content and evidence IDs out of the audit envelope. The existing provenance bridge emits metadata-only details, including an output digest and explicit untrusted marker.
- Uses the request's SQLAlchemy transaction: the provenance writer flushes, then the endpoint commits before returning. Retrieval/audit failures roll back and fail closed.

## API behavior

The response includes the request ID, query, retrieved evidence, and bounded provenance metadata. The query and raw tool output are returned to the authenticated caller but are not written into the provenance audit detail. Tool output is always marked untrusted; marker detection is diagnostic, not a security boundary.

## Validation

Contract tests cover route registration/authentication, strict request validation, tenant override rejection, and explicit read-only tool configuration. CI must run the full Python test suite, lint, migration checks, and production build before merge.

## Remaining limitations

- Retrieval is lexical; no embedding provider or durable vector index is enabled by this endpoint.
- The plan is fixed to one tool rather than generated by an LLM.
- PostgreSQL-backed endpoint transaction tests and human-reviewed prompt-injection cases remain follow-up acceptance work.
